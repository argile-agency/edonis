# Phase 05.1 Plan 05: Settings policy, controller, routes and tests Summary

The server half of `/admin/settings` is in place: an admin-only policy, two routes behind `auth` + `role admin`, a controller whose `show` renders the 12-key page contract and whose `update` saves one tab at a time. Each effective save writes exactly one `admin.settings.update` audit row (changed keys only) in the same transaction. 25 functional tests cover access, validation, audit, the singleton row, a fresh database and mass assignment.

## What was built

- **Policy** `PlatformSettingsPolicy.manage` returns `user.hasRole('admin')` ("Admin only in v1 (D-01): managers excluded"). It is registered in `app/policies/main.ts` and called first in both actions.
- **Routes**: `GET /admin/settings` and `PUT /admin/settings/:tab`, with `:tab` restricted by `.where()` to `appearance|home|access|contact` (anything else is 404). Both carry `middleware.auth()` + `middleware.role({ roles: ['admin'] })`.
- **show**:
  - `getOrCreateActive()` creates the row on a fresh database (D-14).
  - `activeTab` comes from `request.qs().tab`; unknown values fall back to `appearance`.
  - `toPageSettings()` is an explicit 12-key mapping (never `serialize()`). `socialLinks` always has the four keys, with `''` or missing sent as `null`. `allowRegistration` goes through `Boolean()`.
- **update**:
  - The validator is picked from `appSettingValidators[tab]` and given `meta.appHost`.
  - `db.transaction` → `getOrCreateActive(trx)` → manual diff via `normalize()` (`''`/undefined → null, 0/1 → boolean, socialLinks → four-key object, compared with `JSON.stringify`).
  - When keys changed: merge + save + `AuditService.logFromContext(..., trx)` with `oldValues`/`newValues` for the changed keys only, and `metadata { tab, changedKeys }`.
  - Flash « Réglages enregistrés. » or « Aucune modification à enregistrer. », then redirect to `/admin/settings?tab=<tab>`.
- **D-14 statement** (controller header): single-instance in v1. `app_settings` is an `is_active` singleton without `tenant_id`, `getOrCreateActive()` creates the row on a fresh database, and every save updates that row.

## Notes required by the plan

- **Known UI-SPEC deviation:** non-admins get the role middleware's JSON 403 (same as `/admin/audit-logs`), not the Inertia error page. This was an orchestrator decision: the shared role middleware is unchanged in this phase. The policy refusal (Inertia 403 page via the exception handler) would only show for a request the middleware let through. The tests assert the 403 status only and test the policy directly. The owner accepts or rejects this in the 05.1-06 walkthrough.
- **No cache added:** `config/inertia.ts` keeps one query per request, so there is nothing to invalidate.
- **Legacy values:** saving a tab whose stored legacy values now fail validation (for example an old foreign-host logo URL) shows field errors until the admin corrects them.
- **Handoff from 05.1-04, not verified here:** that `router.replace` rewrites `?tab=` without a server request needs a browser. Functional tests cannot prove it, so it moves to the 05.1-06 walkthrough. The same applies to the real Inertia submit and the Referer redirect on a validation error.

## Deviations from Plan

1. **[Rule 3 - Blocking] Validator type widened.** TypeScript cannot call `validateUsing` on the union of the four validators, so `appSettingValidators[tab]` is assigned to `VineValidator<any, { appHost: string }>`. There is no runtime change.
2. **Audit shape for socialLinks.** The audit stores the normalised four-key object even when the row ends up storing SQL NULL because all four links are empty. This follows the plan's "normalised values" wording.
3. **Commits split test/feat** following the executor TDD protocol; the plan named one commit per task.
4. **Test isolation:** each test deletes `app_settings` rows inside the global transaction, as 05.1-01 does, so every test starts from an empty table.
