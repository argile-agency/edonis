# Phase 05.1: Code Review Report

**Reviewed:** 2026-11-04
**Depth:** deep
**Files Reviewed:** 28 (`git diff eef25f4..HEAD -- app inertia start database tests resources config`)
**Status:** issues_found

## Summary

Phase 5.1 adds `/admin/settings`, the `PlatformSettingsPolicy`, per-tab validators, server-side registration enforcement, and the rendering of settings on the home page, header, and favicon. The walkthrough fixes (switch track colour, avatar focus ring) are also in scope.

The security-relevant parts hold up under the checks below. No critical issue was found.

- **Authorization.** The route uses `auth` + `role(['admin'])`, and the controller also calls the policy in both actions.
- **Mass assignment.** VineJS drops unknown keys, including `headerHtml`, `isActive` and unknown `socialLinks` keys; all three were probed.
- **Tab parameter.** The route regex constrains `:tab`, so an unknown tab returns 404 and cannot reach `appSettingValidators[undefined]`.
- **URL validation.** `javascript:`, `data:`, `//host`, `/\host` and `/<TAB>/host` are refused, and so are unknown social keys and emails with a `?cc=` suffix.
- **Stored XSS.** The announcement is rendered as plain React text. The favicon is escaped by Edge `{{ }}`. Footer links go through `isSafeLink`, and `mailto:` is a fixed prefix.
- **Registration.** It is enforced on `GET /register`, on `POST /register` before validation, and on the OAuth first login (D-16). The only other `User.create` is in the admin-only `users_controller.ts`, and no raw `users` inserts exist.
- **Save and audit.** They run in one transaction.
- **Booleans and JSON.** Booleans go through `Boolean()` / `consume` on every read path, and JSON goes through `jsonColumnConfig`.
- **Accessibility test.** The axe spec scans all four tabs, which is needed because Radix unmounts inactive tabs.

The issues are below the security line. The main one: required text fields accept whitespace-only input, which leaves a NULL `app_name` / `hero_title` in the database. There are also two UX defects on the settings and home pages, and a test gap on D-16.

Accepted decisions are not reported: the JSON 403 from the role middleware, root-relative/same-origin images only, the first-visit singleton race, and no settings cache.

## Warnings

### WR-01: Whitespace-only `appName` / `heroTitle` pass validation and are stored as NULL

**File:** `app/validators/app_setting.ts:75`, `app/validators/app_setting.ts:88`; persisted by `app/controllers/app_settings_controller.ts:34`
**Issue:** `vine.string().trim().maxLength(n)` has no minimum length.

1. VineJS's implicit `required` check only rejects `undefined`/`null`.
2. The bodyparser's `convertEmptyStringsToNull` only converts `''`, and `trimWhitespaces` is off.
3. So `"   "` passes, is trimmed to `''`, and the controller's `normalize()` turns `''` into `null`. `row.merge` then writes `app_name = NULL`; the column is nullable in `1763311341500_create_create_app_settings_table.ts`.

This was verified by running the compiled validator: `{ appName: '   ' }` → `{"appName":""}` and `{ heroTitle: '   ' }` → `{"heroTitle":""}`.

**Failure scenario:** An admin clears the "Nom de la plateforme" field with spaces (or pastes a blank value) and saves.
- The toast says « Réglages enregistrés. ».
- On every page, the header logo becomes `<img alt={null}>` (`app-header.tsx:126`), which is missing alt text and is a critical axe violation. When there is no logo, `<h1>` is empty (`app-header.tsx:130`).
- The footer reads « © 2026 . Tous droits réservés. » (`home.tsx:262`).
- The social icons are announced as « null sur Facebook » (`home.tsx:252`).
- `heroTitle` gives an empty hero `<h1>` (`home.tsx:284`).

Both fields are marked « (obligatoire) » in the UI.

**Fix:**
```ts
appName: vine.string().trim().minLength(1).maxLength(100),
// ...
heroTitle: vine.string().trim().minLength(1).maxLength(150),
```
Add `'minLength': 'Ce champ est obligatoire.'` to the messages provider and a unit test for `'   '`.

### WR-02: A root-relative support URL is rendered through Inertia `<Link>`, which breaks for anything that is not an Inertia page

**File:** `inertia/pages/home.tsx:240-245`
**Issue:**
- The validator explicitly allows paths for `supportUrl` (`linkUrl({ allowPath: true })`), and the help text invites « chemin commençant par / ».
- Non-external values are rendered with Inertia's `<Link>`, which makes an XHR visit with `X-Inertia: true`.
- A static file or any non-Inertia route sends back a non-Inertia response.

**Failure scenario:** The admin sets « Page d'aide » to `/offline.html` (exists in `public/`) or `/uploads/aide.pdf`. A visitor clicks « Aide et support ». Instead of navigating, Inertia v2 opens its error modal (an iframe with the raw HTML or PDF response).
**Fix:** Use a plain anchor for paths. Full-page navigation is correct for an arbitrary admin-chosen path.
```tsx
{supportUrl && (
  <a href={supportUrl} {...(isExternalUrl(supportUrl) && { target: '_blank', rel: 'noopener noreferrer' })}
     className="text-sm text-muted-foreground hover:text-foreground transition">
    Aide et support
  </a>
)}
```
After this change, `Link` is still imported and used elsewhere in `home.tsx`.

### WR-03: Saving one tab silently discards unsaved edits in the other three tabs

**File:** `inertia/pages/admin/settings.tsx:144-169`, `inertia/pages/admin/settings.tsx:188-190`
**Issue:**
- The four `useForm`s are hoisted to page level so that « edits survive a tab switch » (comment at line 144).
- But `preserveState: 'errors'` remounts the page on a successful save (comment at lines 188-189), so all four forms are re-initialised from the server props.

**Failure scenario:**
1. The admin edits the hero title on « Page d'accueil » and switches to « Apparence ».
2. They change the colour and click « Enregistrer l'apparence ».
3. The toast says « Réglages enregistrés. », and the hero title edit is gone without any warning.

The page explicitly promises that edits survive a tab switch, so the admin has no reason to expect this loss.
**Fix:** Pick one of these:
- Keep state on success too (`preserveState: true`) and reset only the saved form with `form.setDefaults()` in `onSuccess`. The flash toast still fires because `FlashMessages` depends on `flash.success`, but identical consecutive messages need a key such as a timestamp.
- Or warn before switching tabs when another form is `isDirty`.

### WR-04: D-16 (no account creation via OAuth when registration is closed) has no automated test

**File:** `app/controllers/social_auth_controller.ts:71-75`; tests `tests/functional/registration_closed.spec.ts` (covers only `GET`/`POST /register`)
**Issue:** No test exercises the OAuth callback with registration closed. Running `grep -rl "isRegistrationOpen|REGISTRATION_CLOSED|allowRegistration" tests/` finds no social-auth spec, and `tests/functional/` has no social-auth spec at all. Two branches are unprotected:
- the refusal path (a new email gives no `User` and no `UserRole`);
- the pass-through for existing accounts, where the check must stay inside `if (!user)`.

**Failure scenario:** A later refactor moves the check, for example above `User.findBy` or outside the `if`. Either existing users can no longer log in with Google or GitHub, or accounts are created again on a closed platform. CI stays green in both cases.
**Fix:** Add a functional test with a faked Ally driver. `@adonisjs/ally` lets `ally.use()` be swapped through the container, or `SocialAuthController.callback` can be stubbed with a fake `social.user()`. Assert three cases:
- closed + unknown email → redirect `/login`, flash `REGISTRATION_CLOSED_MESSAGE`, `User.findBy('email')` is null;
- closed + existing email → logged in;
- open + unknown email → user created.

## Info

### IN-01: Same-host check accepts URLs that the browser blocks anyway (`http://` on an https site, `user:pw@`)

**File:** `app/validators/app_setting.ts:32-38`
**Issue:**
- The check compares `url.host` only, so `http://demo.edonis.org/logo.png` passes on the https deployment. The browser then blocks it as mixed content, and CSP `'self'` does not cover the downgrade.
- `https://user:pw@demo.edonis.org/a.png` also passes (verified). Chromium blocks subresources with embedded credentials.

Either way, the result is a saved setting that renders a broken image.
**Fix:** Also require `url.protocol === request.protocol() + ':'` (pass it in `meta`) and `!url.username && !url.password`. Alternatively, accept only root-relative paths and drop the absolute form.

### IN-02: `appHost` comes from `request.host()`, which the admin's own request controls

**File:** `app/controllers/app_settings_controller.ts:77`
**Issue:** `request.host()` is the `Host` header, or `X-Forwarded-Host` from a trusted proxy (loopback by default).
- An admin using curl can send `Host: evil.example` and store `https://evil.example/x.png` as an "image of this site".
- This is not exploitable cross-site, because browsers cannot forge `Host` in a CSRF request.
- CSP `imgSrc 'self'` still blocks the load, so the impact is a broken image only.

There is a second effect behind a proxy that rewrites `Host` without `X-Forwarded-Host`, such as Infomaniak's k8s ingress if configured that way. The legitimate absolute URL `https://demo.edonis.org/...` is then refused, while root paths keep working.
**Fix:** Compare against a configured origin (an `APP_URL` env value) instead of the request header. Alternatively, keep only root-relative paths (see IN-01).

### IN-03: The seeded « Réglages de la plateforme » user-menu item is never rendered

**File:** `database/seeders/menu_seeder.ts:190-202`; `config/inertia.ts` (shares `menus.userMenu`)
**Issue:** No component renders `menus.userMenu`. A grep shows it only in TypeScript prop interfaces (`app-header.tsx:73`, `home.tsx:139`, `dashboard.tsx:48`, `courses/index.tsx:97`). The real entry point is the hard-coded item at `app-header.tsx:236-243`. The D-02 seeder row is dead data: renaming or deactivating it in the DB has no effect, and someone who later wires `userMenu` gets a duplicate entry.
**Fix:** Either drop the seeder row, or render `menus.userMenu` in the header dropdown and remove the hard-coded item.

### IN-04: Header logo and favicon skip the `isSafeImageSrc` guard used for the hero image

**File:** `inertia/components/layout/app-header.tsx:125-126`, `resources/views/partials/favicon.edge:1-3`
**Issue:** `safe_url.ts` says legacy rows never passed the validator, yet only `heroImageUrl` is filtered. A legacy `appLogoUrl` or `appFaviconUrl` is emitted as-is. A value such as `javascript:` or a foreign host gives no script execution in `img src` or `link rel=icon`, and Edge escapes the value. So this is an inconsistency, not a vulnerability.
**Fix:** Wrap the logo with `isSafeImageSrc(settings.appLogoUrl)`. For the favicon, filter in `config/inertia.ts` or with an Edge global so the three image fields share one rule.

### IN-05: The production row's old `contact_email` will now be shown publicly

**File:** `inertia/pages/home.tsx:213-228`; `database/seeders/app_setting_seeder.ts` (old default `support@edonis.local`)
**Issue:** Before this phase, `contactEmail` was not rendered anywhere. A row seeded with the old seeder, which is the likely case for demo.edonis.org since production does not run `db:seed` again, holds `support@edonis.local`. That value is a valid email, so it passes the new validator. After deploy, it appears as a `mailto:` link in the public footer.

The post-deploy steps in `05.1-06-SUMMARY.md` only ask the admin to fix values that are *rejected*, so this one can be missed. Old `socialLinks` `''` values are handled correctly (normalised to null).
**Fix:** Add « vérifier l'adresse de contact (ancienne valeur support@edonis.local) » to the post-deploy checklist, or add a one-off data migration that replaces that exact value.

### IN-06: Concurrent saves are last-write-wins with stale audit `oldValues` (pre-existing pattern, low impact)

**File:** `app/controllers/app_settings_controller.ts:80-91`
**Issue:** `getOrCreateActive(trx)` reads without a row lock. With two admins saving the same tab at the same time:
- both diffs are computed against the same snapshot;
- the second save overwrites the first;
- the second audit row records `oldValues` that were never the actual previous state.

Impact is low with a single admin, and this is separate from the accepted fresh-DB insert race.
**Fix:** `AppSetting.query({ client: trx }).where('is_active', true).forUpdate().first()` on PostgreSQL/MySQL; SQLite serialises writers anyway. Fall back to create when null.
