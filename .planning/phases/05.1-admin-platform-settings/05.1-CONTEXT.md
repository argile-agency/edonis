# Phase 5.1: Admin platform settings - Context

**Gathered:** 2026-11-03
**Status:** Ready for planning
**Source:** Owner brief (`.planning/todos/completed/2026-11-03-admin-platform-settings-page.md`) and the owner's decisions of 2026-11-03, treated as a PRD (discuss-phase skipped: every gray area was decided)

<domain>
## Phase Boundary

One admin-only page, `/admin/settings`, to edit the singleton `AppSetting` row (`is_active = true`) from the UI, so a deployed instance (the public demo at demo.edonis.org first) can be changed without a database edit or a deploy. Every setting exposed on the page has a visible effect.

Not in this phase: per-course or per-user settings, environment variables (`TERMS_VERSION`...), file upload, custom HTML, multi-tenant settings.

</domain>

<decisions>
## Implementation Decisions

### Page and layout
- **D-01:** Route `/admin/settings`, admin only (managers excluded in v1). Tabs with the existing `inertia/components/ui/tabs.tsx`: **Apparence**, **Page d'accueil**, **Accès**, **Contact et support**. One form per tab, each saved independently.
- **D-02:** Entry point: an admin item in the user menu (`database/seeders/menu_seeder.ts`; it is registered in `database/seeders/main/index_seeder.ts`).
- **D-03:** French labels; every input labelled; field errors tied with `aria-describedby`; tabs keyboard-navigable; an axe-core browser test (critical/serious) for the page. Success toast through the existing flash toaster.

### Fields per tab (owner decision 4: « Brancher ceux qui comptent »)
- **D-04 Apparence:** app name, logo URL, favicon URL, primary colour (`#RRGGBB`). Secondary and accent colours are **not** exposed (no effect).
- **D-05 Page d'accueil:** hero title, hero subtitle, hero image URL, announcement text (D-09). `welcomeMessage`, `showStats` and `showPublicCourses` are **not** exposed (`welcomeMessage` duplicates the hero; the other two are not enforced anywhere and stay out of v1).
- **D-06 Accès:** allow registration. It must be **enforced server-side** on `GET /register` and the register POST (refused or redirected with a French message when off), and the "Inscription" links hidden when off. Verified 2026-11-03: nothing reads `allowRegistration` on the server today.
- **D-07 Contact et support:** contact email, support URL, social links (facebook, twitter, linkedin, github only).

### Wiring of each exposed field (a setting that does nothing must not be editable)
- **D-08:** contact email, support URL and social links render in the footer; favicon renders as `<link rel="icon">` in the Edge layout (`resources/views/`); hero image renders in the public hero of `home.tsx`; app name, logo and primary colour keep their current rendering (`app-header.tsx`); hero title and subtitle keep theirs (`home.tsx`).

### Announcement banner (owner decision 2)
- **D-09:** New optional plain-text column `announcement_text` on `app_settings` (cross-engine, reversible migration with `down()`), rendered as plain text (never HTML) at the top of the home page when set. It **replaces** the demo banner hard-coded in `inertia/pages/home.tsx` (commit `2fc5399`); `app_setting_seeder.ts` sets the default « Environnement de démonstration — un projet pilote ? contact@edonis.org » (the address may be turned into a `mailto:` link at render time by matching the contact email; no HTML is ever stored).

### Security
- **D-10 (owner decision 1):** `headerHtml` and `footerHtml` are **not** exposed in v1 (raw HTML on every page is an XSS vector, even admin-only). The columns stay untouched.
- **D-11:** VineJS validator in `app/validators/`: trimmed strings with max lengths, `#RRGGBB` colours, valid email, `http(s)`-only URLs (or root-relative paths, see D-15), `socialLinks` limited to the four known keys. Invalid input is rejected field by field in French, nothing persisted.
- **D-12:** Authorization in the controller as well as the route middleware (`middleware.auth()` + `middleware.role({ roles: ['admin'] })`), per CLAUDE.md "check both authentication AND authorization". Teacher, manager, student get 403; anonymous visitors are redirected to login.
- **D-13:** One `AuditService.logFromContext(ctx, ...)` row per save, metadata = changed keys with old and new values.

### Data and engines
- **D-14 (owner decision 5):** Single-instance in v1: `app_settings` keeps the `is_active` singleton without `tenant_id`; this is stated explicitly in the code (model or controller comment) and the SUMMARY. A fresh database without a settings row must work: the page creates the row instead of crashing (`AppSetting.getActiveSettings()` can return null). Saves update the singleton, never insert a second active row. Any new column through `database/helpers/schema_helpers.ts`; JSON (`socialLinks`) with `typeof` guards (CLAUDE.md). Works on PostgreSQL, MySQL/MariaDB and SQLite.
- **D-15 (owner decision 3):** Logo, favicon and hero image are URL fields in v1; upload comes later. **Constraint found while writing this context:** the CSP in `config/shield.ts` allows images only from `'self'`, `data:` and `blob:` (`imgSrc`), so an external `https://` logo, favicon or hero image is blocked by the browser. The planner must resolve it: either accept root-relative paths and same-origin URLs only (e.g. `/uploads/logo.png`, served by the app) and say so in the field help, or extend `imgSrc` with an explicit, minimal rule. Widening the CSP is a security change: if chosen, it needs its own justification in the plan's threat model. Default: root-relative paths and same-origin URLs only.

### Claude's Discretion
- Exact Lucid/Inertia shape of the props, whether one `update` action takes a `tab` discriminator or there is one action per tab.
- Whether to cache `appSettings` (one query per request today, `config/inertia.ts`); if no cache is added, say so in the SUMMARY.
- Seeder default values, as long as they match the new defaults and stay realistic and minimal.

</decisions>

<specifics>
## Specific Ideas

- Acceptance criteria (from the brief): an admin changes each exposed setting and sees it on the public home page and in the header without a deploy; other roles get 403, anonymous a login redirect; invalid input (bad colour, bad email, `javascript:` URL, oversized text) rejected with French field errors and nothing persisted; one audit row per save with the changed keys; works on a fresh database; works on the three engines; functional tests (200 admin, 403 others, validation, audit row, singleton updated not duplicated) and a browser a11y test; seeder defaults match; `bun run lint && bun run typecheck && bun run build && node ace test` green.
- The `© 2024` footer and the "Certificats" card were already fixed in `2fc5399` (hard-coded in `home.tsx`, not settings).
- The pending todo `2026-10-20-course-creation-requests-with-save-and-publish-buttons.md` expects a "course creation requests" platform setting later: this page is where it will live; not in this phase.

</specifics>
