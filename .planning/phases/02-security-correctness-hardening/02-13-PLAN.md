<objective>
Make enrolment counters correct by construction. Today every counter mutation is a read-modify-write on an in-memory attribute (`method.currentEnrollments += 1; save()`). A transaction alone would not stop two concurrent enrolments from both passing `isAvailable()` and over-filling a capacity-limited method. `forUpdate()` compiles to nothing on SQLite. `unenroll` never decrements the method counter, and the seeders write fake `enrolled_count` values. **No `db.transaction` exists anywhere in `app/` today.**

This plan adds an `EnrollmentService`:
- it runs each enrolment inside `db.transaction()`
- it uses **atomic conditional `UPDATE ... SET x = x + 1 WHERE (max IS NULL OR x < max)`** with an affected-row check
- it relies on the existing `unique(course_id, user_id)` constraint as the duplicate guard, caught outside the transaction callback

It also adds a recount command, and rewires the four enrolment actions in `enrollments_controller.ts`. Admin `addParticipant`/`removeParticipant` (`courses_controller.ts`) follow in plan 02-14.

Purpose: DEBT-06, reworded success criterion 3.

- `EnrollmentService`
- the rewired controller
- `node ace enrollment:recount`
- `enrollment_counters.spec.ts`
</objective>

Lucid 21.8 / knex 3.1:
- `db.transaction(async (trx) => {...})` is a managed transaction: it commits on resolve and rolls back on throw.
- `Model.query({ client: trx })`, and `Model.create(data, { client: trx })`.
- `.increment(col, n)` / `.decrement(col, n)` on the model query builder skip hooks and `updatedAt`, which is fine for counters.
- Lucid returns write-query results as an array (`return Array.isArray(rows) ? rows : [rows]`, `query_builder/index.js:124-133`), so `const [affected] = await ...increment(...)` gives the affected-row count. That knex yields a **number** for `pg`, `mysql2` and `better-sqlite3` is [ASSUMED AS7]. This plan's tests are the proof, and they run on the CI pg/mysql/sqlite matrix.
- On SQLite, `forUpdate()` compiles to `''`. Do NOT use it.
- Under `withGlobalTransaction()`, the app's `db.transaction()` becomes a savepoint, so a service rollback undoes only its savepoint.
- A unique violation on PostgreSQL aborts the transaction, which is why the catch must sit OUTSIDE the `db.transaction` callback. Error codes: PG `code === '23505'`; MySQL/MariaDB `code === 'ER_DUP_ENTRY'` (errno 1062); SQLite (better-sqlite3) `code === 'SQLITE_CONSTRAINT_UNIQUE'` [ASSUMED; the CI matrix proves it]. Also accept `SQLITE_CONSTRAINT` together with a message containing `UNIQUE`.
