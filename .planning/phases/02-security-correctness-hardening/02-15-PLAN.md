<objective>
Close verification gap CR-02: `GET /courses/:id/enroll` (`EnrollmentsController.show`) has no policy call and ships every enabled enrolment method through `method.serialize()`, which includes the plaintext `enrollmentKey`. Any logged-in user can read the key of any course and pass `enrollWithKey`, voiding the AS4 key gate.

Purpose: DEBT-04 ("authorization applied uniformly"); verification truth 7.
Output: key hidden from default serialization (manager page sends it explicitly), learner-facing whitelist on the enrolment page, a new `CoursePolicy.viewEnrollmentPage` rule applied in `show`, and a regression spec.

Design decisions (planner, justified):
- Whitelist fields are derived from what `inertia/pages/enrollments/show.tsx` reads, NOT from the verifier's shorter list. The page's `isMethodAvailable` returns false when `isEnabled` is missing, and it also reads `approvalMessage`, `enrollmentStartDate`, `enrollmentEndDate`, `maxEnrollments`, `currentEnrollments`. Dropping them would hide every enrolment form.
- Gate rule `viewEnrollmentPage = course.canEnroll() OR view`. A `view`-only rule would refuse private and unlisted courses that are open for enrolment and reached by a shared link (key enrolment for those would become impossible), which nobody approved. The `canEnroll` leg keeps that flow; the `view` leg keeps the page readable for public courses even when closed (the page then shows its "not available" state). The only newly refused requests are for courses that are neither viewable nor open for enrolment, where AS4 already refuses every self/key enrolment, so no user-visible flow that worked before is removed. No checkpoint; the gate still ships as its own commit so it can be reverted alone.
- `serializeAs: null` on the model is defence in depth: any future `serialize()` of a method (or of a relation that preloads one) can no longer leak the key.
</objective>
