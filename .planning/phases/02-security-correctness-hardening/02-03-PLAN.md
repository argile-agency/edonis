<objective>
Give the half-finished 2FA login (password accepted, TOTP pending) an explicit lifetime and an attempts budget. Today it is a bare `session.put('two_factor_user_id', id)`:
- no expiry, so it lives as long as the 2-hour session
- no attempt cap
- throttling is per IP only, so a distributed attacker who knows the password gets 5 guesses per minute per IP

Purpose: DEBT-09, first half (the explicit timeout). Plan 02-08 delivers the documented recovery path (admin reset, CLI break-glass, doc). The plan also moves `two_factor_controller`'s inline validators into `app/validators/two_factor.ts`, including the per-request `vine.compile` anti-pattern in `verifyRecovery`. That is DEBT-05 consistency work on a file this plan already owns.

Output:
- a pure pending-state helper with unit tests
- controllers switched to `{ userId, expiresAt, attempts }`
- a per-user `twoFactorThrottle`
- hoisted validators
- a functional spec for the 2FA flow
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Password-verified but not 2FA-verified client → challenge endpoints | Attacker holding a stolen password probes TOTP codes |
| Session cookie → server | Pending state lives in the encrypted cookie session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Spoofing | TOTP brute force across many IPs | mitigate | `twoFactorThrottle` keyed on `2fa_user_<id>` (5/min, block 15 min) in addition to per-IP `loginThrottle`; plus 5-attempt lock per pending state. |
| T-02-12 | Spoofing | long-lived half-login | mitigate | 10-minute TTL enforced by `readPending` on every challenge request; unit-tested boundary. |
| T-02-13 | Tampering | client-modified / replayed pending state | accept | The cookie session is encrypted and signed, so a client cannot forge `{userId, expiresAt, attempts}` without APP_KEY. It **can replay** an older cookie that still holds a lower `attempts` value. The 5-attempt cap is therefore defence in depth only. The **authoritative brute-force control is the server-side per-user `twoFactorThrottle`** (memory/limiter store, keyed `2fa_user_<id>`), together with per-IP `loginThrottle`. Replay cannot extend the TTL, because `expiresAt` is set once at password verification and travels inside the signed value. |
| T-02-14 | Repudiation | expiry / lockout invisible to admins | mitigate | Audit rows `user.login.2fa_expired` and `user.login.2fa_locked` with `resourceId`. |
| T-02-15 | Denial of Service | attacker locking a victim's pending login | accept | Lock only destroys the attacker-held pending state (it lives in the attacker's own session); the legitimate user's separate session is unaffected. The per-user limiter can block the victim's challenge for 15 min — accepted, matches CLAUDE.md rate-limit requirement. |
| T-02-16 | Spoofing | legacy `two_factor_user_id` key | mitigate | Legacy key is forgotten and never honoured; test asserts redirect to login. |
</threat_model>
