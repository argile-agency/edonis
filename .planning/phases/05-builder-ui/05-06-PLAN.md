<decisions_applied>
- **Props contract (the builder only):** `course: { id, title, code }` (no longer the full `course.serialize()`, so less payload and no instructor fields), `sections: BuilderSection[]`, `contents: BuilderContent[]`, shapes as in `inertia/lib/builder_tree.ts`.
  - Two flat queries in `builder`. Modules: `where('course_id', course.id)`, with `select('id', 'parent_id', 'title', 'description', 'order', 'is_published', 'available_from', 'available_until', 'updated_at')`. Contents: `whereIn('module_id', <subquery of those module ids>)`, selecting `id`, `module_id`, `content_type`, `title`, `description`, `order`, `is_published`, `available_from`, `available_until`, `updated_at`, and never `content` (page bodies).
  - Map each row explicitly to the contract fields (dates `toISO()`), not `serialize()`: `serializeExtras` would compute `isAvailable` / `isOverdue`, which are useless here.
  - Keep `authorize('edit', course)`. `learn`, `outline`, `getCourseProgress` and `CoursesController.show` are NOT touched; they stay 2-level by design (D-02 revised).
- **Legacy level-3 sections** (rows with `tooDeep`) are shown with the badge "Niveau 3 : invisible pour les apprenants". They offer no "+ Contenu" and no "+ Sous-section", and the teacher can move them back with "Déplacer vers…" (research assumption A3, decided in 05-01).
- **"+ Sous-section"** renders only on rows with `section.parentId === null` (D-02). Today it is rendered on children too, which is how invisible third-level sections were created.
- **Initial expansion:** every section starts expanded, so the plan is visible at once. The old page started collapsed; this is a discretionary visual default, not a rule change. `expanded` is local state keyed by section id and survives prop refreshes.
- **Newly created sections open automatically (BUILD-04 / BUILD-07):** `knownSectionIdsRef` (a `Set<number>`) is seeded at mount with every section id. Each time new props are applied (re-sync rule below), every section id not in it is added to `expanded` and to `knownSectionIdsRef`; ids already known keep the teacher's collapsed or expanded choice, so a refresh never re-opens a section the teacher closed. Opening "+ Contenu" on a section also adds that section to `expanded`. Result: content added through "+ Contenu", including into a section created a moment ago, is visible at once.
- **Optimistic ops** (one `SaveOp` per user action, built in the page). Snapshots and tokens are read from refs (`sectionsRef`, `contentsRef`) at the moment they are needed. The token is read inside `run`, not at enqueue time.
  - `apply`: snapshot `{ sections, contents }` into the op closure, then set the new local state (with `applyContentMove`, `applySectionMove`, a title or field patch, or row removal).
  - `run`: `sendJson` to the endpoint with the current token of the item, read from the ref at run time. On success, write the returned `item.updatedAt` into the item.
  - `rollback(err)`: restore the op's snapshot. Rollbacks run in reverse order, so restoring each snapshot is consistent.
    - For a title op with `err.kind === 'conflict'`: after the restore, patch the item with `err.body.item` (fresh title and token), then reopen the editor with `initialDraft` = the typed value and `errorMessage` = the conflict text (D-09: input kept). Saving again then overwrites knowingly.
    - For a details op on conflict: patch the fresh token only and set the panel's `errorMessage`. The panel keeps its local field values.
- **Synchronous state writes (token race guard):** every write to `sections` / `contents` goes through one helper per array, `commitSections(next)` / `commitContents(next)`. Each assigns `ref.current = next` synchronously, then calls `setState(next)`. That covers `apply`, the success token write in `run`, `rollback`, and the prop re-sync. Never assign the refs during render or in an effect: the queue starts the next op's `run` in a microtask, before React re-renders, so a ref updated late would send the previous token and the teacher would conflict with their own save (false "modifié par un autre enseignant" on two quick actions).
- **Prop re-sync (queue-aware):** keep the latest props in `latestPropsRef` (`{ sections, contents }`, updated whenever the props change) and the props last applied in `appliedPropsRef` (set at mount). One effect, depending on the two props and on `queue.pending`, applies `latestPropsRef.current` through `commitSections` / `commitContents` (plus the auto-expand above) only when `queue.pending === 0` AND `latestPropsRef.current` differs from `appliedPropsRef.current` (compare the `sections` and `contents` arrays by identity: Inertia sends new arrays on every visit), then sets `appliedPropsRef.current = latestPropsRef.current`. Props that arrive while saves are in flight (an Inertia creation, a "Recharger") are therefore applied as soon as the queue drains, and the drain itself never re-applies old props over the newer optimistic state.
- **"Recharger"** (conflict or session errors): `router.reload({ only: ['sections', 'contents'], onFinish: () => queue.dismiss() })`.
- **Focus management:**
  - after a menu move: focus the moved row's actions trigger
  - after a delete: focus the next row's title button, else the previous row's, else the parent section's (computed before removal, applied in an effect via a `pendingFocusId` state)
  - after rename or cancel: InlineTitle restores focus itself
- **Creation** stays an Inertia `useForm.post`, with `preserveScroll: true`, and keeps the existing dialogs, fields and type `Select` (page, video, file, link, assignment, quiz). Tighten the `any` types (`auth.user`, `appSettings`, `menus`, and the `Select` `onValueChange` value typed as `ContentType`).
- **No drag code in this plan.** The `GripVertical` handle and dnd-kit arrive in 05-07. Remove the old decorative `GripVertical`, `Edit` and `Trash2` buttons now.
