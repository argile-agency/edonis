<decisions_applied>
- **Token is optional on updates.** `updatedAt: vine.string().nullable().optional()`. Absent (`undefined`) means no conflict check, which keeps the existing Inertia callers and the 02-10 tests unchanged. Present, including `null`, means `sameSecond` (from 05-01) is checked. The update is not wrapped in the course lock: a check-then-save on one row is enough, and the same-second blind spot is already documented in 05-01.
- **The `...payload` trap.** Both update actions spread `payload` into `merge()`. `updatedAt` MUST be destructured out first (`const { updatedAt: expected, availableFrom, availableUntil, ...changes } = payload`). Otherwise the string overwrites the timestamp column.
- **VineJS 3.0.1 semantics (verified in `node_modules/@vinejs/vine/build/src/schema/base/main.d.ts`):** `.optional()` accepts `null` on input but outputs `undefined`, which is the WR-20 root cause. `.nullable().optional()` outputs `null | undefined`. `config/bodyparser.ts` has `convertEmptyStringsToNull: true` for every parser, so a cleared description arrives as `null` and needs `.nullable()` too.
- **Date mapping:** `undefined` leaves the field untouched, `null` sets `null`, and a `Date` becomes `DateTime.fromJSDate(...)`. The order check runs after merging the payload with the stored values: if the resulting `availableFrom` and `availableUntil` are both set and `availableFrom > availableUntil`, the response is 422 JSON `{ errors: [{ field: 'availableUntil', message: 'La date de fin doit être postérieure à la date de début.' }] }`, or flash + back for HTML. Nothing is saved.
- **Delete-content copy and data:** deleting a content item cascades its `content_progress` rows (existing behaviour, accepted by D-06 until the trash phase; the confirmation in 05-05 says so) and its `content_content_files` pivot rows. `content_files` rows and blobs are NOT deleted, because they may be shared.
- **Legacy deep sections:** `createContent` into a section whose depth is greater than `MAX_SECTION_DEPTH` gives flash `DEPTH_ERROR` + back, and nothing is created. This is D-02 applied to contents, for the same reason as in 05-01: that level is invisible to learners.
- **Not a behaviour change for users:** the JSON branches are new paths. The HTML paths only gain the D-02 / D-05 refusals the user approved, plus the WR-20 date-order refusal requested in planning.
</decisions_applied>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (teacher) → update/delete/create endpoints | Payload, token and ids are untrusted |
| Teacher A ↔ teacher B | Concurrent edits and deletes on one course |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-13 | Tampering (data loss) | `deleteModule` vs concurrent move | mitigate | Course-row `forUpdate()` and the emptiness re-check inside one transaction (both FKs cascade); 409 when not empty (tested) |
| T-05-14 | Tampering (lost update) | `updateModule` / `updateContent` | mitigate | Optional `updatedAt` token → 409 with the fresh item; the token is destructured out of the merge payload |
| T-05-15 | Tampering (mass assignment) | `...payload` spread into `merge` | mitigate | VineJS whitelists fields; `updatedAt`, `parentId` (removed in 05-01) and dates are handled explicitly |
| T-05-16 | Spoofing (CSRF) | JSON callers | mitigate | Shield unchanged; test proves a JSON caller without a token gets 302 and nothing is written |
| T-05-17 | Elevation of Privilege | update/delete routes | mitigate | Existing `authorize('edit', item's course)`; 403 JSON tested for an outsider |
| T-05-18 | Information Disclosure | 409 body returns the fresh item | accept | Only to a user who already passed `edit` on that course |
</threat_model>
