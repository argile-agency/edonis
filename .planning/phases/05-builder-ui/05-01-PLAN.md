<objective>
Build the server half of drag-and-drop: two intent-based JSON endpoints that move a content item or a section to `(destination, position)`. They recompute the order of every touched sibling list on the server, under a per-course row lock, in one transaction.

- `POST /contents/:contentId/move` body `{ moduleId, position, updatedAt }`: BUILD-01 (same section) and BUILD-02 (other section, including an empty one, D-03).
- `POST /modules/:moduleId/move` body `{ parentId, position, updatedAt }`: BUILD-03 and D-01 (re-parenting with cycle protection). D-02 revised: at most 2 levels (section > sub-section), counting the moved section's own sub-tree.
- D-09: the `updatedAt` token is compared to the second. A stale token gives 409 with the fresh row.
- Open question Q4 (decided): `parentId` is dropped from `updateModuleValidator`, so re-parenting has a single path through `moveModule` and its depth check. The A8 `updateModule` test of plan 02-10 moves to the new endpoint.

Purpose: every later plan (menu moves, drag, optimistic UI) calls these endpoints. The old `reorderModules` / `reorderContents` routes stay in place, unused by the new UI, and keep their tests (02-10).

Output: pure helpers `depthOf` / `subtreeHeight` with unit tests, two validators, two routes, two controller actions, `tests/functional/builder_moves.spec.ts`, and the updated A8 test.
</objective>

<decisions_applied>
- **D-02 depth rule (revised: 2 levels).** Depth is 0-based: a root section has depth 0 and a sub-section depth 1. The server constant is `MAX_SECTION_DEPTH = 1`, a non-exported `const` in the controller with a one-line comment "0-based: root = 0, sub-section = 1 (D-02: 2 levels)". A section move is refused when `newDepth + subtreeHeight(moved) > MAX_SECTION_DEPTH`. RESEARCH.md says "3 levels" and `> 2` everywhere; ignore those numbers (see the override table at the top of PATTERNS.md).
- **Legacy data deeper than 2 levels (open question Q3, decided):** left as is. No migration. The builder will show it at its real depth (plan 05-06). A move that keeps it too deep is refused, and a move that brings it back within the limit is accepted. Because a third-level section is invisible to learners (that is why D-02 exists), a content item may not be moved INTO a section whose depth is greater than `MAX_SECTION_DEPTH` (422, same message). This applies D-02 to contents; it is not a new rule.
- **Conflict token (open question Q1, decided): `updated_at` compared to the second, no new column.** Lucid writes `updated_at` with seconds precision on SQLite and MySQL and with milliseconds on PostgreSQL, so compare `DateTime.fromISO(expected).toUnixInteger()` with `row.updatedAt?.toUnixInteger()`. Both null counts as equal. An unparseable ISO string counts as a mismatch. Why not `lock_version`: it would need a reversible migration on two tables, model hooks, and seeder/factory updates across three engines. The only gain is catching two different teachers saving the same item within the same second, which `updated_at` misses. That blind spot is accepted and documented with a `shortcut:` comment on the comparison helper ("same-second writes by two users are not detected; switch to a lock_version column if that ever matters").
- Only the moved row is saved through the model, so `autoUpdate` bumps its `updatedAt`. Renumbered siblings are written with the query builder (no `updated_at` bump), so a move does not invalidate other teachers' tokens on the siblings.
- **Position semantics (shared with the client mirror in 05-02, keep identical):** `position` is the 0-based index among the destination siblings, with the moved item excluded, ordered by `(order, id)`. It is clamped to `[0, n]`. Destination siblings are renumbered densely `1..n+1`. When the parent changes, the source siblings are renumbered `1..m` too. Only rows whose `order` actually changes are written.
</decisions_applied>
