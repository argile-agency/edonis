- **D-11 scope, server side:** six routes (below), one per action family; publish and unpublish share one route with an `isPublished` flag.
- **D-12:** `copied_from_id` on both tables, set on every duplicated row (top-level copies and the copied children). No UI, no exposure in the builder props, no sync.
- **Payload items:** every action takes `items: { kind: 'section' | 'content'; id: number; updatedAt: string | null }[]` (1..1000 entries; duplicates of the same `kind:id` are collapsed). 1000 bounds the work of one request (T-05-36) while staying above any realistic course, so "Tout sélectionner" → "Publier" (roadmap criterion 7, no normalisation for publish) never hits the cap; 15 sections × 15 contents is only 240 rows. The client sends the whole selection and does not check the cap.
- **D-09 on bulk actions:** every item carries its token. Inside the transaction, after the lock, if any item fails `sameSecond(row.updatedAt, item.updatedAt)` (05-01 service export), the whole batch is refused with 409 `{ code: 'E_CONFLICT', message: CONFLICT_ERROR, items: [{ kind, id, updatedAt }] }` (the stale rows, fresh tokens), and nothing is written.
- **Scope (IDOR, same discipline as 02-10):** the course comes from `params.id`; sections are loaded with `where('course_id', courseId)`, contents with `whereIn('module_id', <subquery of the course's module ids>)`. Any requested id not found that way → 422 `{ code: 'E_INVALID_ITEMS', message: 'Certains éléments ne font pas partie de ce cours.', ids: [{ kind, id }] }`, nothing written. A missing course gives the HTML 404 of `firstOrFail` (as everywhere in this controller family).
- **One lock, one transaction, one audit row.** Each action runs `db.transaction(async (trx) => { ... })`: course-row lock `Course.query({ client: trx }).where('id', courseId).forUpdate().first()` (inline, same idiom as 05-01 / 05-04), load and scope the items, check the tokens, then the action. A refusal inside the callback throws a local `class BulkRefusal extends Error { constructor(public status: 409 | 422, public body: Record<string, unknown>) }`; the managed transaction rolls back, and a `try/catch` outside the callback turns it into the JSON response (EnrollmentService pattern, 02-13: the catch sits outside the callback because PostgreSQL aborts the transaction on errors). Other errors are rethrown. After a commit: exactly one `AuditService.logFromContext(ctx, ...)`, then the 200 response.
- **Audit row (ids only):** `{ action, resourceType: 'Course', resourceId: courseId, metadata }`. `metadata` keys:
  - every action: `sectionIds: number[]`, `contentIds: number[]` (the selected ids, sorted ascending)
  - `course.bulk.shift_dates`: plus `days: number`
  - `course.bulk.move`: plus `parentId: number | null`
  - `course.bulk.duplicate`: plus `createdSectionIds: number[]`, `createdContentIds: number[]`
  - action names: `course.bulk.publish`, `course.bulk.unpublish`, `course.bulk.availability`, `course.bulk.shift_dates`, `course.bulk.move`, `course.bulk.duplicate`, `course.bulk.delete`

- **200 response (the 05-03 `sendJson` contract, consumed by 05-10):** `{ sections: BuilderSection[], contents: BuilderContent[], affected: { sectionIds: number[]; contentIds: number[] }, deleted: { sectionIds: number[]; contentIds: number[] } }`. `sections` / `contents` are the course's whole fresh structure from `loadBuilderStructure(courseId)` (read after the commit). `affected` lists the rows whose server state the client must take: every row this action saved or created (their `updatedAt` changed, so the client needs the fresh tokens), plus, for move and duplicate, every row of each sibling list the action renumbered (source and destination lists, computed from the post-commit structure as "all sections whose `parentId` is a touched parent, all contents whose `moduleId` is a touched section"). Renumbering itself does not bump `updated_at` (query builder, as in 05-01), so those rows keep their tokens; listing them only gives the client their new `order`. `deleted` lists the removed ids, including the descendants of deleted sections.
- **Writes bump tokens only when something changes.** Rows are saved through the model (`useTransaction(trx)`, `merge`, `save`), so `autoUpdate` bumps `updatedAt`, and only rows whose values actually change are saved and listed in `affected`.
- **Tree order (shared with the client in 05-10, keep identical):** the order in which a batch is processed is the order of `buildRows(sections, contents, <every section id expanded>)` from `builder_tree` (05-02): a section, then its contents by `(order, id)`, then its sub-sections, recursively; roots by `(order, id)`. Import `buildRows` and the types from the module path recorded in `05-02-SUMMARY.md` (A7: `../../inertia/lib/builder_tree.js` or the `app/helpers/builder_tree.ts` fallback).
- **Normalisation for structural actions (move, duplicate, delete):** an item whose ancestor section is also selected is dropped from processing (it travels with that ancestor). Publish, availability and date shift apply to every selected item individually (no cascade to children).
- **Publish / unpublish (BUILD-12):** sets `isPublished` on each selected item. No cascade.
- **Availability window (BUILD-13):** `availableFrom` and `availableUntil` are both required keys, each a date or `null` (`null` clears). If both are set and `availableFrom > availableUntil` → 422 `{ errors: [{ field: 'availableUntil', message: 'La date de fin doit être postérieure à la date de début.' }] }` (same message as 05-04). - **Move (BUILD-14):** `parentId: number | null`. - **Duplicate (BUILD-14, D-12):** in tree order after normalisation:
  - a content: a copy in the same section, placed right after its original (siblings renumbered densely with `CourseStructureService.renumber`), title + ` (copie)`, `copiedFromId = original.id`, every other column copied from `original.$attributes` except `id`, `createdAt`, `updatedAt`, `order` and `isPublished` (see OQ-2). Its `content_content_files` pivot rows are copied (`course_content_id` = the copy, same `content_file_id`, `filename`, `mime_type`, `created_at` = now).   - depth: a copy sits at its original's depth, so the 2-level limit holds by construction. - **Delete (BUILD-14, D-05 kept for single deletes). OQ-3 — RESOLVED 2026-10-31 (the owner accepted this default; raised by the plan checker):** single deletes keep 05-04's rule (empty sections only). This relaxes the letter of D-05 / D-06 (no non-empty section deletable in phase 5) on the strength of D-11 ("delete (confirmation required)"), and it cascades learner progress; the fallback if the user says no is `false` = any non-empty section in a bulk delete is refused with the same 409. The teacher has then explicitly chosen everything that goes, which is the intent of D-05 / D-06 ("nothing of value is lost by accident"); a section with anything unselected inside would cascade-delete unchosen items, so the whole batch is refused with 409 `{ code: 'E_NOT_EMPTY', message: "Sélectionnez aussi tout le contenu des sections à supprimer.", ids: [<blocking section ids>] }` and nothing is deleted. The client also requires the confirmation dialog (05-10). Contents are deleted with the query builder, then the top-level selected sections (FK cascades remove the covered descendants, which are all selected). Remaining siblings are not renumbered (same as 05-04's single delete; the `(order, id)` semantics tolerate gaps). Learner progress on deleted contents cascades, exactly like 05-04's single delete; the 05-08 walkthrough asks the user about it for single AND bulk delete.
- **Migration on SQLite (data-loss trap, verified in `node_modules/knex/lib/dialects/sqlite3/schema/ddl.js` and `@adonisjs/lucid` `migration/runner.js`):** on SQLite, knex adds a foreign key to an existing table by rebuilding it (create a copy, copy the rows, drop the original, rename). It switches `PRAGMA foreign_keys` off for that, but SQLite ignores the pragma inside a transaction, and Lucid wraps every migration in a transaction by default. With `foreign_keys = ON` (`config/database.ts`), dropping the original `course_modules` would cascade-delete its contents, sub-sections and progress. The migration therefore sets `static disableTransactions = true`, with a comment saying why. On PostgreSQL and MySQL the two `alterTable` calls are plain DDL (MySQL DDL is not transactional anyway). Task 1's verify proves on a seeded SQLite DB that up → down → up keeps every row.
