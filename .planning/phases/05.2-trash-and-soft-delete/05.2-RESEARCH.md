#### Carried forward (Phase 5 CONTEXT D-06, ROADMAP § 05.2, Phase 5 walkthrough 2026-11-03)

- **D-03:** The Phase 5 « empty section only » rule (D-05) is lifted: a non-empty section can be deleted (with its sub-sections and contents), after confirmation.
- **D-04:** Retention configurable in the platform administration (`/admin/settings`, Phase 5.1).

#### Restore
- **D-05:** Restoring a content whose section is also in the trash opens a dialog: « Restaurer aussi la section « X » » or « Restaurer dans une autre section… » (same destination list as « Déplacer vers… », depth rules unchanged).
- **D-06:** A restored section returns to its original parent and position when that parent still exists (siblings shift to make room); otherwise at the end of the root sections.
- **D-07:** Restoring a section brings back everything trashed with it in the same delete operation (sub-sections, contents). Items that were trashed separately before the section stay in the trash. Implies a delete-operation identifier (batch id) stored on each trashed row.
- **D-08:** Assignments linked to a trashed section (`assignments.module_id`) are hidden with it and come back with it. Submissions and grades are never deleted, even at purge: at purge the assignment is only detached from the section (`module_id` set to null, as the current `ON DELETE SET NULL` does).

#### Permissions
- **D-09:** Viewing the trash and restoring: every course editor (owner, collaborators with edit or manage permission, admins) — the same people who can delete, through `CoursePolicy`.
- **D-10:** Permanent delete of one item and « Vider la corbeille »: course owner and admins only (collaborators can restore, not erase).
- **D-11:** No platform-wide admin trash: admins use each course's trash.

#### Purge
- **D-12:** Two triggers: an ace command `node ace trash:purge` meant for a nightly cron (Infomaniak cron; documented in the SUMMARY and the deployment notes), plus a lazy purge of the course's expired items whenever its trash page is opened, so purging happens even without the cron.
- **D-13:** At purge, a stored file (`ContentFile`) is deleted from disk only when no remaining content (trashed or not) references it; copies made with « Dupliquer » share blobs.
- **D-14:** Retention setting: integer days, 1 to 365, default 30, in a new « Corbeille » tab of `/admin/settings` (same conventions as Phase 5.1: VineJS, French copy, audit row on save, single-instance `app_settings`, cross-engine migration). Lowering it applies to items already in the trash at the next purge.
- **D-15:** No e-mail warning. Each trash row shows the days left, in a warning colour at 3 days or fewer.

#### Display
- **D-16:** A dedicated page `/courses/:id/trash`, reachable from a « Corbeille (N) » button in the builder header and a link in the course page « Contenu » tab.
- **D-17:** Each row shows: title, type, original section, deleted by and when, days left. (The learner count is not shown in the list; it stays in the delete and permanent-delete confirmations.)
- **D-18:** After a delete in the builder, a toast « « X » déplacé dans la corbeille. » with an « Annuler » action (about 10 seconds) restores in one click.
- **D-19:** The delete confirmation dialog stays (single and bulk), with the adapted text of D-02.

## Summary

Lucid 21 has no built-in soft delete, but its model hooks are the documented way to build one. A `@beforeFind` + `@beforeFetch` (+ `@beforePaginate`) hook on `CourseModule` and `CourseContent` that appends `whereNull('<table>.deleted_at')` runs on every model query that returns instances, **including preloads and `related().query()`**. Preloads call `.exec()` (`node_modules/@adonisjs/lucid/build/src/orm/preloader/index.js:41,70`), and `exec()` and `first()` run the hooks when `wrapResultsToModelInstances` is true (`orm/query_builder/index.js:359-365,609-617`). [VERIFIED: Lucid source in node_modules] [CITED: lucid.adonisjs.com/docs/model-hooks]

That one change covers almost every read path in the inventory below with no per-call edit. It works because of an invariant the phase must preserve: **a live content always has a live section, and a live section always has a live parent.** Trashing always takes the whole subtree; the hooks already stop anything from being created in or moved into a trashed section; restoring a content into a trashed section is refused (D-05). Only the hooks' blind spots need explicit care: `pojo()`, `db.from()`/`trx.from()` raw queries, `whereHas` subqueries, `Assignment` queries and the trash service itself. Those blind spots are also the natural escape hatch for reading trashed rows.

Purge becomes today's hard delete. The existing cascades (contents → progress and file pivots, sections → sub-sections and contents, `assignments.module_id` SET NULL) already do the right thing once the rows are physically deleted. Trashing never triggers them, because it is an `UPDATE`. Blob refcounting needs no new column: the pivot rows of trashed contents still exist, so a blob is orphaned only when its last pivot is physically gone.

**Primary recommendation:** add the hook on both models; add one `TrashService` (trash, restore, purge, list) built on `trx.from()` raw writes plus `CourseStructureService` for placement; one `TrashController` and Inertia page; a `trash` settings tab. No dependency is added.

### Hook mechanism (exact)

```typescript
// app/models/course_module.ts (same in course_content.ts with CourseContent)
import { beforeFetch, beforeFind, beforePaginate } from '@adonisjs/lucid/orm'
import type { ModelQueryBuilderContract } from '@adonisjs/lucid/types/model'

type Q = ModelQueryBuilderContract<typeof CourseModule>

@column.dateTime() declare deletedAt: DateTime | null
@column() declare deletedBatch: string | null
@column() declare deletedById: number | null

// Trashed rows are invisible to every model query (preloads included). Read them with trx.from().
@beforeFind()
static hideTrashedOnFind(query: Q) { query.whereNull(`${CourseModule.table}.deleted_at`) }
@beforeFetch()
static hideTrashedOnFetch(query: Q) { query.whereNull(`${CourseModule.table}.deleted_at`) }
@beforePaginate()
static hideTrashedOnPaginate([count, query]: [Q, Q]) {
  count.whereNull(`${CourseModule.table}.deleted_at`)
  query.whereNull(`${CourseModule.table}.deleted_at`)
}
```
Source: lucid.adonisjs.com/docs/model-hooks (its `filterDeleted` example; paginate must filter both queries). Qualify the column: `files_controller.ts:80` joins the pivot table. Keep the `deleted_at` column out of `builder_props` and out of the `serialize()` used in props, or leave it, since it is always null on live rows.

### Trash write path
- Inside the existing lock transaction, compute the subtree from `loadBuilderStructure(courseId, trx)` (live rows). Include descendant sections up to `MAX_SECTION_DEPTH` and their contents.
- `batch = randomUUID()`, `now = DateTime.now().toFormat(trx.dialect.dateTimeFormat)` (precedent `course_bulk_actions_controller.ts:214`).
- `trx.from('course_modules').whereIn('id', sectionIds).whereNull('deleted_at').update({ deleted_at: now, deleted_batch: batch, deleted_by_id: userId })`, and the same for contents. Do **not** bump `updated_at`.
- Do not renumber the remaining siblings (gaps are fine, as today, `course_bulk_actions_controller.ts:510`). The trashed rows keep their `order`, which restore uses.
- Single `deleteModule`: remove the emptiness check (`course_contents_controller.ts:391-406`) and the `E_NOT_EMPTY` branch. `deleteContent` (`:558-580`) today runs with no transaction or lock; wrap it in the same lock transaction.
- Bulk `destroy`: drop the `blocking`/`E_NOT_EMPTY` block (`:524-547`) and `BULK_DELETE_ALLOWS_FULL_SUBTREE` (`:36-38`). A selected section takes its whole subtree, selected or not, per D-03. One batch for all `topLevelItems(scope)`.
- Responses: single `{ item: { id }, batch }`; bulk keeps its shape plus `batch`, and `deleted` must include every descendant id (the client already removes them with `bulkDeletedIds`).
- Audit: keep the action names `course.module.delete` / `course.content.delete` / `course.bulk.delete` (existing audit viewers and tests use them) and add `batch` plus the descendant ids to `metadata`. Ids only.

### Restore algorithm
Definitions:
- **Batch root:** a trashed row whose parent (section for a content, `parent_id` for a section) is not trashed in the same batch. Trash list rows are batch roots.
- **restore(X):** X plus the rows of X's batch that descend from X. Other batches stay trashed (D-07). Restore must accept **any** trashed section, not only roots. The D-05 option « Restaurer aussi la section » can target a sub-section that was trashed as part of its parent's batch.
- **restoreBatch(b):** every root of b, in ascending stored `order` within each parent (the undo toast).

Steps (one transaction, course lock):
1. Load the target row with `trx.from(table).where('id', id).whereNotNull('deleted_at')` and scope it to the course (contents via `module_id` → `course_modules.course_id`). Missing or not trashed gives 404 `E_NOT_IN_TRASH`, which also covers double restore and two editors racing.
2. Content whose section is still trashed: return 409 `{ code: 'E_PARENT_TRASHED', section: { id, title } }` unless `withSection: true` (restore that section first, steps 3-5, then continue) or `moduleId` (a live section from the move-target list).
3. `position` = number of live siblings whose `(order, id)` sorts before the stored `(order, id)` of the restored row.
4. Clear `deleted_at`, `deleted_batch` and `deleted_by_id` on the restored set (raw update), then reload the target with `CourseModule.query({ client: trx })`. It is live now, so the hook lets it through.
5. Call `CourseStructureService.moveModule(trx, courseId, row, parentIdOrNull, position)` or `moveContent(...)`. Clearing first matters: `parentMap` and `subtreeHeight` then see the restored sub-sections, so the depth check is correct. A case that needs it: the original parent was later moved under another section, so restoring a section with sub-sections under it would exceed 2 levels.
   - If the parent is not live, or the move returns `E_DEPTH`/`E_INVALID_DESTINATION`, call `moveModule(trx, courseId, row, null, Number.MAX_SAFE_INTEGER)` (the end of the root sections, D-06; position is clamped at `:136`).
   - For a content with an explicit `moduleId`, a refusal returns 422 and the transaction rolls back.
   - `save()` bumps `updatedAt`, so restored rows get fresh conflict tokens.
6. Audit `course.trash.restore` `{ courseId, batch, sectionIds, contentIds, toParentId }`. Respond in the **bulk shape** `{ ...loadBuilderStructure(courseId), affected, deleted: emptyIds() }`, where `affected` = restored ids plus the renumbered siblings (reuse `withRenumbered`), so the builder's `mergeBulkResult` (`inertia/lib/builder_tree.ts:722`) applies it unchanged.

Assignments (D-08) need no write: hiding comes from the gradebook filter (#20), so restoring the section brings them back automatically.

### Trash list
`trx.from('course_modules')` and `course_contents` (join `course_modules` for `course_id` and the original section title), filtered `whereNotNull('deleted_at')`. LEFT JOIN `users` on `deleted_by_id`; show « Utilisateur supprimé » when null or dangling. Keep roots only. Sort by `deleted_at desc, id desc`.
- Each row: `kind, id, title, type, originalSection, deletedBy, deletedAt (ISO), daysLeft, batch, descendantCount, contentIds` (every trashed content under it, any batch, for the permanent-delete learner count).
- `daysLeft = ceil(deletedAt + N days − now)` in days, computed in the controller from the current setting (D-14).
- Pagination: not needed for v0.1. Shortcut comment: a course trash is small; paginate if a course ever exceeds about 200 roots.
- `Corbeille (N)`: builder props gain `trash: { count, retentionDays }`. `count` = number of roots, computed by the same service.

### Purge
`TrashService.purgeExpired({ courseId?, now?, trigger: 'cli' | 'page' })`:
1. `N = (await AppSetting.getOrCreateActive()).trashRetentionDays`. Compute `cutoff = DateTime.now().minus({ days: N }).toFormat(dialect.dateTimeFormat)` **in the app**. Never use DB `NOW()`/interval arithmetic (not portable; SQLite `CURRENT_TIMESTAMP` is UTC text). SQLite compares the strings, so the same format on write and on compare is mandatory. Expiry is derived at read time (no `expires_at` column), which is what makes D-14's "lowering applies at next purge" true.
2. Cron: course ids = `SELECT DISTINCT course_id FROM course_modules WHERE deleted_at < cutoff` UNION the contents joined to modules. One transaction per course, so one failure does not block the others; the exit code is non-zero if any course failed.
3. Per course, under the course lock, `forceDelete(trx, courseId, expiredRoots)`:
   - Gather **all** content ids that will disappear: the expired contents, plus every content (any batch) under the expired sections. Cascaded contents must be included, or their blobs leak.
   - `candidates = SELECT DISTINCT content_file_id FROM content_content_files WHERE course_content_id IN (…)`.
   - Defensive: refuse to delete a section that still has a live descendant (it cannot happen under the invariant). Log and skip.
   - `DELETE course_contents WHERE id IN (…)` (cascades progress and pivots: `1763370620773…:19-24`, `1792402903468…:13-19`), then `DELETE course_modules WHERE id IN (expired sections)` (cascades sub-sections; `assignments.module_id` SET NULL, `1763377052525…:16-22`). Chunk `whereIn` lists (SQLite variable limit; `PIVOT_CHUNK` precedent).
   - Orphans: `SELECT id, storage_path FROM content_files WHERE id IN (candidates) AND NOT EXISTS (SELECT 1 FROM content_content_files p WHERE p.content_file_id = content_files.id)`, then delete those ids with the same `NOT EXISTS` guard.
   - Audit `course.trash.purge` `{ courseId, trigger, sectionIds, contentIds, fileIds }` with `AuditService.log(…, trx)` (no ctx on the CLI, precedent `enrollment_service.ts:278`); the page trigger uses `logFromContext`.
4. After commit: `FileStorageService.deleteBlob(storagePath)` (new method: `resolvePath()`, then `unlink`, ignoring ENOENT; never throws). A failed unlink leaves a stray file with no DB row. That is harmless, and a later upload of the same bytes creates a fresh row and path.
5. Idempotent: the second run finds nothing. Cron and page purges on the same course serialize on the course lock.
6. Page-open purge: call it in `TrashController.index` before listing, wrapped in try/catch with a log. A purge failure must not break the page.

Permanent delete (one root) and « Vider la corbeille » call the same `forceDelete`, with the action names `course.trash.delete` / `course.trash.empty`. Permanent delete of a section also removes contents trashed earlier under it (FK cascade). The confirmation must count them (`descendantCount` and `contentIds` on the row).

**Accepted race:** an upload of the same bytes can run `ContentFile.findBy(checksum)` (`file_storage_service.ts:106`) just before the orphan delete; its pivot insert then fails on the FK (500, user retries). The window is milliseconds at night. Shortcut comment in code.

**Ace command:** `commands/trash_purge.ts`, `commandName = 'trash:purge'`, `options = { startApp: true }`, `--dry-run` flag (precedent `commands/enrollment_recount.ts`). It logs per course and per count. Keep the command thin; test the service directly.

**Infomaniak cron:** run from `build/`: `cd build && node ace trash:purge` (the app runs from `build/` and `.env` lives there, per deployment notes). Whether the managed Node.js hosting offers scheduled tasks is **not verified** [ASSUMED]. The lazy purge (D-12) is the fallback, so the plan's SUMMARY should say "cron optional".

### Anti-Patterns to Avoid
- **Unqualified `whereNull('deleted_at')`** in the hook: ambiguous on joined queries (pivot). Always prefix the table name.
- **Ungrouped `orWhere` on these models:** the hook appends `AND deleted_at IS NULL`, so `a OR b AND deleted_at IS NULL` leaks trashed rows. Group with `.where(q => q.where(a).orWhere(b))`.
- **`NOT IN` with NULLs:** the gradebook filter written as `whereNotIn('module_id', trashed)` drops assignments with `module_id IS NULL` (`NULL NOT IN (…)` is not true). Use `whereNull('module_id').orWhereNotIn(...)` inside a group.
- **Relying on cascade to find blobs:** collect the pivot file ids of every content that disappears (cascaded included) **before** the delete.
- **Unlinking blobs inside the transaction:** a rollback would leave DB rows pointing at deleted files. Commit first, then unlink.
- **`Model.refresh()` or `Model.find()` on a trashed row in restore code:** the hook hides it. Use `trx.from()`. (No `.refresh()` exists in `app/` today, checked by grep.)
- **Bumping `updated_at` when trashing:** it is harmless, but restore already bumps it through `save()`, so avoid the extra write.
- **Renumbering siblings at trash time:** that loses the stored position D-06 needs.

## Migration Design (cross-engine)

`1793700000000_add_trash_columns_to_course_structure.ts`:
```typescript
// SQLite: dropColumn in down() rebuilds the table (copy, drop, rename; knex
// dialects/sqlite3/schema/ddl.js dropColumn → alter()). Inside a transaction the
// foreign_keys pragma cannot be turned off, so dropping course_modules would cascade.
static disableTransactions = true

async up() {
  this.schema.alterTable('course_modules', (t) => {
    t.timestamp('deleted_at').nullable()
    t.string('deleted_batch', 36).nullable()
    t.integer('deleted_by_id').unsigned().nullable() // no FK: see below
    t.index(['course_id', 'deleted_at'])
    t.index(['deleted_batch'])
  })
  this.schema.alterTable('course_contents', (t) => {
    t.timestamp('deleted_at').nullable()
    t.string('deleted_batch', 36).nullable()
    t.integer('deleted_by_id').unsigned().nullable()
    t.index(['module_id', 'deleted_at'])
    t.index(['deleted_batch'])
  })
}
async down() { /* dropIndex ×2 then dropColumn ×3, per table */ }
```
- **No FK on `deleted_by_id` (recommended).** Adding an FK on SQLite makes knex rebuild the whole table (copy, drop, rename). Inside a transaction SQLite ignores `PRAGMA foreign_keys=OFF`, so dropping the original `course_modules` would cascade-delete contents and progress. That is why `1793500000000_add_copied_from_id_to_course_structure.ts:7-10` needs `disableTransactions = true`. Plain nullable columns and indexes are a simple `ALTER TABLE ADD COLUMN` in `up()`. **But `down()`'s `dropColumn` rebuilds the table on SQLite** (`node_modules/knex/lib/dialects/sqlite3/schema/ddl.js:128` → `alter()` `:335-352`: copy, drop original, rename; the FK pragma is left as-is when inside a transaction). So `static disableTransactions = true` is **mandatory** on this migration, FK or not.
  - Users are hard-deleted at `users_controller.ts:332`, so the id can dangle; the trash list LEFT JOINs and shows « Utilisateur supprimé ».
  - If the planner prefers an FK: `.references('id').inTable('users').onDelete('SET NULL')`, copy the `disableTransactions` pattern exactly, and in `down()` drop the FK before its index (MySQL, `1793500000000…:34`).
- `deleted_at`: `timestamp` nullable, the same definition as `available_from`/`available_until` on both tables (`1763370524278…:37-38`, `1763370568724…:42-43`), which already pass the CI MySQL matrix as nullable NULL-default columns. `ADD COLUMN` compiles the column definition the same way.
- Indexes: modules `(course_id, deleted_at)` serves the lists and the purge scan. Contents have no `course_id`, so `(module_id, deleted_at)` plus a join.
- Read-back: `deleted_at` goes through `@column.dateTime()`. Raw `trx.from()` reads return a `Date` (pg, mysql2) or a string (SQLite); parse both with `DateTime.fromJSDate` / `fromSQL`, or keep the parsing in one helper. Booleans are not involved. PostgreSQL returns `count(*)` as a string: use `Number()` (precedent `course_bulk_actions_controller.ts:593`).
- **Manual migration check (SQLite), up and down:** seed, count modules/contents/progress/pivots, migrate, count, `migration:rollback`, count again. The functional suite migrates an empty DB and cannot catch row loss. The `app_settings` migration needs no flag (nothing references that table).

## Common Pitfalls

### Pitfall 1: SQLite timestamp text comparison
**What goes wrong:** the purge deletes nothing, or everything.
**Why:** SQLite stores datetimes as text, and `<` compares strings. A cutoff in ISO with `T`/zone against stored `yyyy-MM-dd HH:mm:ss` compares wrong.
**How to avoid:** write and compare with `toFormat(trx.dialect.dateTimeFormat)` only. Add a unit/functional test with rows at N−1 and N+1 days (set `deleted_at` by raw update).
**Warning signs:** the purge test passes on SQLite with a "now" fixture but not with crafted dates.

### Pitfall 2: Hook blind spots
**What goes wrong:** trashed rows leak through `pojo()`, `db.from()`, `whereHas`, or `Assignment`.
**How to avoid:** use the inventory above, `trash_visibility.spec.ts`, and the `check:debt` grep.

### Pitfall 3: Breaking the live-parent invariant
**What goes wrong:** a live content sits under a trashed section. It is reachable through `learn?content=` while the outline hides it, and purge cascades it away (data loss).
**How to avoid:** trash always takes the whole subtree. Restore of a content into a trashed section is refused (409 `E_PARENT_TRASHED`). Purge's defensive live-descendant check logs and skips.

### Pitfall 4: Undo before the delete has committed
**What goes wrong:** the toast appears at enqueue time, the user clicks « Annuler », and there is no batch yet.
**How to avoid:** toast from `run()` after success. Undo is itself a queue op.

### Pitfall 5: Existing tests that encode the old rules
- `tests/functional/builder_moves.spec.ts:1060-1095` (E_NOT_EMPTY JSON and flash)
- `tests/functional/builder_bulk.spec.ts:~720-730` (E_NOT_EMPTY)
- `tests/browser/builder.spec.ts:284-286` (disabled « Supprimer » with reason)
- `tests/browser/builder_bulk.spec.ts:357-362` (blocked bulk delete)
- `tests/unit/builder_tree.spec.ts:349-353,477-483`

Rewrite them to the new behaviour. Assertions like `assert.isNull(await CourseContent.find(id))` (`builder_bulk.spec.ts:699-705,749-750`) **still pass** because of the hook; extend them with a raw check that the row exists with `deleted_at` set and that progress and pivot rows are kept.

### Pitfall 6: Purge after D-08
After purge, the assignment's `module_id` is NULL, so it **reappears**, unattached, in the gradebook. This follows from D-08 (grades never deleted). Document it in the UI help text or the SUMMARY; no code needed.

### Pitfall 7: Lowering retention mass-deletes on the next page open
Dropping retention from 365 to 1 purges almost the whole trash of a course as soon as its trash page opens. Mention it in the settings help text (D-14 accepts this behaviour).
