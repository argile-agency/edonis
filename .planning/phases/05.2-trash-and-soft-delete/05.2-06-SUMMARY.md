# Phase 05.2 Plan 06: Restore and trash list Summary

`TrashService` can now restore. A row goes back to its original `(order, id)` place along with the rows of its own batch. If that place is gone or would be deeper than 2 levels, it goes to the end of the root sections. A content whose section is trashed is refused with 409 unless the caller passes `withSection` or `moduleId`. `restoreBatch` restores a whole batch or nothing. `list` returns the batch roots for the trash page.

## Exported contract (for 05.2-09)

```ts
export type RestoreTarget = { kind: 'section' | 'content'; id: number }
export type RestoreOptions = { withSection?: boolean; moduleId?: number }
export type RestoreResult = {
  outcome: Outcome            // auditAction 'course.trash.restore', affected, batch, touchedParents, touchedSections
  title: string; batch: string
  sectionIds: number[]; contentIds: number[]
  restoredSection: { id: number; title: string } | null
  destination: { id: number; title: string } | null
  fallback: boolean
}
export type TrashListRow = {
  kind: 'section' | 'content'; id: number; title: string; type: string | null
  originalSection: { id: number; title: string } | null
  sectionTrashed: { id: number; title: string } | null
  deletedBy: string | null; deletedAt: string; daysLeft: number; batch: string
  descendantCount: number; contentIds: number[]
}
TrashService.restore(trx, courseId, target, options?)
TrashService.restoreBatch(trx, courseId, batch)
TrashService.list(courseId, retentionDays, client, now = DateTime.now())
```

Refusals are thrown as `BulkRefusal`:
- 404 `E_NOT_IN_TRASH`
- 409 `E_PARENT_TRASHED`, with `section: { id, title }`
- 422 `E_INVALID_DESTINATION` or `E_DEPTH`, from an explicit `moduleId`

Outside a transaction, pass `db.connection()` to `list`.

## Deviations from Plan

**1. [Rule 1 - Bug] A fresh conflict token on every restored row**
- **Found during:** Task 1
- **Issue:** The behaviour "restored rows get a fresh updated_at" did not hold. When a row went back to its old order and parent, the move's `save()` found nothing dirty and wrote nothing. Descendants never go through `save()` at all.
- **Fix:** `clear()` now sets `updated_at` in the same raw update that clears `deleted_*`.
- **Commit:** 650c12e

**2. Small refactor:** the write loop in `trash()` used a local chunked-write closure. It now uses a shared `inChunks` helper that `clear()` also uses. Behaviour is unchanged and `trash.spec.ts` is still green.
