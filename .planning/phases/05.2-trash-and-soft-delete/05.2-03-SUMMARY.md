# Phase 05.2 Plan 03: Builder deletes go to the trash Summary

Every builder delete (single section, single content, bulk) now moves the selected rows and their whole live subtree to the trash. It goes through `TrashService.trash`, under one `randomUUID()` batch, inside the course-lock transaction, with one audit row written in the same transaction. The builder page receives `trash: { count, retentionDays }`. `GET /courses/:id/progress` no longer counts sub-section contents twice.

## Contracts for downstream plans

**Exports of `app/helpers/builder_ids.ts` (12):** `PIVOT_CHUNK`, `Kind`, `Item`, `Ids`, `Structure`, `Outcome`, `BulkRefusal` (status `404 | 409 | 422`), `emptyIds`, `push`, `sorted`, `idsOf`, `withRenumbered`. `topLevelItems(scope)` and `Scope` stay in the bulk controller.

**`Outcome`** gained an optional `batch?: string`.

**Bulk responses:** every bulk action answers `{ sections, contents, affected, deleted, batch }`. `batch` is set only by delete; on the other actions it is `undefined` and drops out of the JSON. For delete, `deleted` = every section and content id that left the live tree (selected rows and all their descendants), sorted. `affected` is empty.

**Single delete responses:** JSON `{ item: { id }, batch }`. HTML redirects back with the flash `success` « « {titre} » déplacé dans la corbeille. ». A section is always deletable.

**Audit rows** (written inside the transaction, action names unchanged):
- `course.module.delete`: `{ courseId, batch, sectionIds, contentIds }`
- `course.content.delete`: `{ courseId, moduleId, batch, sectionIds, contentIds }`
- `course.bulk.delete`: `{ sectionIds, contentIds, batch }`, with every trashed id

**TrashService:**
- `trash(trx, courseId, roots, userId) → { batch, deleted }`. The subtree comes from `loadBuilderStructure(courseId, trx)`. Rows are written raw with `whereNull('deleted_at')`, so an id that is already trashed is a no-op. `order`, progress rows and file pivots are kept.
- `trashedRows(client, courseId)`, `rootsOf(rows)`, `countRoots(courseId, client)`. **Pass `db.connection()`, not `db`**, outside a transaction.
- `toDbDateTime(dt, client)`, `fromDbDateTime(value)`.

## Deviations from Plan

- **[Rule 2 - T-05.2-10] In-transaction existence check.** After taking the course lock, `deleteModule` and `deleteContent` re-fetch their row with `firstOrFail()`. A row trashed meanwhile by another editor now gets a 404 with nothing written. Without this, the request would answer 200 with an empty batch and write an audit row.
- **`db.connection()` instead of `db`.** The builder calls `countRoots(course.id, db.connection())`. The plan's `db` does not typecheck against `QueryClientContract`. 05.2-06 and 05.2-09 should do the same.
- **Content delete audit** keeps `moduleId` next to `batch`, `sectionIds` and `contentIds`.
- **Extra old tests updated in `builder_moves.spec.ts`.** Two more tests encoded the old behaviour: the empty-section and content JSON bodies and audit metadata (now with `batch`), and the content pivot (now kept, `lengthOf 1`, instead of cascaded).
- **Verify commands** were run from the worktree root instead of the main-repo path the plan gives (same as 05.2-01).
