# Phase 05.2 Plan 09: Trash HTTP endpoints Summary

The trash now works over HTTP. `TrashController` is a thin layer over `TrashService` (restore, list) and `TrashPurgeService` (lazy purge, forceDelete, removeBlobs). Opening `/courses/:id/trash` purges the course's expired rows first. A failed purge is logged and never breaks the page. Editors (owner, edit/manage collaborators, admins) can view and restore. Only the owner and admins can delete for good, through the new `CoursePolicy.emptyTrash`. Each mutation writes one audit row with ids only, inside its transaction. Blob files are unlinked only after commit.

## Routes (builder group: auth + role admin|manager|teacher)

| Route | Name | Policy |
|-------|------|--------|
| GET `/courses/:id/trash` | `courses.trash` | edit |
| POST `/courses/:id/trash/restore` | `courses.trash.restore` | edit |
| POST `/courses/:id/trash/restore-batch` | `courses.trash.restoreBatch` | edit |
| POST `/courses/:id/trash/delete` | `courses.trash.delete` | emptyTrash |
| POST `/courses/:id/trash/empty` | `courses.trash.empty` | emptyTrash |

The page props and flash texts follow the TRASH PAGE CONTRACT exactly, and restore-batch follows the RESTORE-BATCH CONTRACT (bulk shape, 404 `E_NOT_IN_TRASH`, 409 `E_PARENT_TRASHED`). The success flash is chosen in this order: fallback, then destination, then restored section, then the plain text.
