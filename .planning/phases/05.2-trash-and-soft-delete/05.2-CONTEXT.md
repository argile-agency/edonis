# Phase 5.2: Trash and soft delete - Context

**Gathered:** 2026-11-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Deleting a section or a content in the builder (single delete, bulk delete) moves it to a per-course trash instead of removing it. Trashed items disappear everywhere for learners and teachers, and their structure, attached files, linked assignments and learner progress are kept until they are restored or purged. The trash lists, restores and permanently deletes; a purge removes items after a configurable retention (30 days by default).

Not in this phase: trash for courses, users, assignments deleted from the assignments page, or any other entity; a platform-wide admin trash; e-mail warnings before purge.

</domain>

<decisions>
## Implementation Decisions

### Carried forward (Phase 5 CONTEXT D-06, ROADMAP § 05.2, Phase 5 walkthrough 2026-11-03)
- **D-01:** Soft delete with `deleted_at` on `course_modules` and `course_contents` (CLAUDE.md conventions); learner progress (`content_progresses`) is kept while an item is in the trash.
- **D-02:** The confirmation before deleting stays, with the count of affected learners (shipped in Phase 5, `d393afb`); its text changes to say the item goes to the trash and is permanently deleted in N days (N = retention setting).
- **D-03:** The Phase 5 « empty section only » rule (D-05) is lifted: a non-empty section can be deleted (with its sub-sections and contents), after confirmation.
- **D-04:** Retention configurable in the platform administration (`/admin/settings`, Phase 5.1).

### Restore
- **D-05:** Restoring a content whose section is also in the trash opens a dialog: « Restaurer aussi la section « X » » or « Restaurer dans une autre section… » (same destination list as « Déplacer vers… », depth rules unchanged).
- **D-06:** A restored section returns to its original parent and position when that parent still exists (siblings shift to make room); otherwise at the end of the root sections.
- **D-07:** Restoring a section brings back everything trashed with it in the same delete operation (sub-sections, contents). Items that were trashed separately before the section stay in the trash. Implies a delete-operation identifier (batch id) stored on each trashed row.
- **D-08:** Assignments linked to a trashed section (`assignments.module_id`) are hidden with it and come back with it. Submissions and grades are never deleted, even at purge: at purge the assignment is only detached from the section (`module_id` set to null, as the current `ON DELETE SET NULL` does).

### Permissions
- **D-09:** Viewing the trash and restoring: every course editor (owner, collaborators with edit or manage permission, admins) — the same people who can delete, through `CoursePolicy`.
- **D-10:** Permanent delete of one item and « Vider la corbeille »: course owner and admins only (collaborators can restore, not erase).
- **D-11:** No platform-wide admin trash: admins use each course's trash.

### Purge
- **D-12:** Two triggers: an ace command `node ace trash:purge` meant for a nightly cron (Infomaniak cron; documented in the SUMMARY and the deployment notes), plus a lazy purge of the course's expired items whenever its trash page is opened, so purging happens even without the cron.
- **D-13:** At purge, a stored file (`ContentFile`) is deleted from disk only when no remaining content (trashed or not) references it; copies made with « Dupliquer » share blobs.
- **D-14:** Retention setting: integer days, 1 to 365, default 30, in a new « Corbeille » tab of `/admin/settings` (same conventions as Phase 5.1: VineJS, French copy, audit row on save, single-instance `app_settings`, cross-engine migration). Lowering it applies to items already in the trash at the next purge.
- **D-15:** No e-mail warning. Each trash row shows the days left, in a warning colour at 3 days or fewer.

### Display
- **D-16:** A dedicated page `/courses/:id/trash`, reachable from a « Corbeille (N) » button in the builder header and a link in the course page « Contenu » tab.
- **D-17:** Each row shows: title, type, original section, deleted by and when, days left. (The learner count is not shown in the list; it stays in the delete and permanent-delete confirmations.)
- **D-18:** After a delete in the builder, a toast « « X » déplacé dans la corbeille. » with an « Annuler » action (about 10 seconds) restores in one click.
- **D-19:** The delete confirmation dialog stays (single and bulk), with the adapted text of D-02.

### Claude's Discretion
- Trashed items are invisible everywhere for learners and teachers (builder, outline, learn page, course page, progress queries, assignment lists tied to a trashed section, file downloads of trashed content); progress percentages are computed without trashed contents and come back on restore.
- Storage of "deleted by" (user id column) and of the delete batch id; ordering of the trash list (most recent first); pagination if needed.
- Whether `trash:purge` and the page-open purge share one service (expected); audit rows for trash, restore, permanent delete and purge (purge audited per course with ids only).
- Bulk delete reuses the same trash path (one batch id per bulk operation); the bulk « Annuler » toast restores the whole batch.
- GDPR: trashed contents are course data, not personal data; learner progress kept in the trash stays covered by the existing export and anonymisation (verify, do not extend scope).

</decisions>

## Existing Code Insights

### Reusable Assets
- `LearnerImpact` component and `POST /courses/:id/builder/delete-impact`: learner count in confirmations.
- `MoveTargetList` / `moveTargets`: destination list for « Restaurer dans une autre section… ».
- `CourseStructureService` (locked moves, depth checks) for restoring into place.
- Save queue (`useSaveQueue`, `sendJson`) and the sonner toast for the « Annuler » action.
- `AppSetting` singleton plus per-tab validators and controller for the retention setting.

### Established Patterns
- Every builder mutation: `CoursePolicy` edit, one transaction under the course row lock, conflict tokens, one audit row with ids only.
- Cross-engine migrations, booleans converted on read, `disableTransactions` on SQLite when needed.

### Integration Points
- Every query that reads `course_modules` / `course_contents` (about 12 files in `app/`) must exclude trashed rows; progress percentage computation; file download authorization (`files_controller.ts`).
- Today's hard-delete cascades become purge-time behaviour; trashing must not trigger them.

</code_context>
